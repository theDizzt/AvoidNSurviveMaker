# 순위표 검증과 콘텐츠 버전

## 저장 경계

- `level_records`: 브라우저가 보고하는 개인 백업. `verified`는 false이며 순위표에 사용하지 않습니다.
- `verified_level_records`: 서버가 공식 맵으로 재생해 얻은 결과만 저장합니다. 일반 클라이언트의 직접 읽기·쓰기는 금지되며 공개 조회는 UUID 없는 `level_leaderboard` RPC만 사용합니다.
- 검증기는 요청의 계정 ID, 맵, 클리어 시간, 별을 받지 않습니다. 인증 토큰을 Auth 서버에 확인하고, 요청의 버전 키로 배포된 공식 맵을 조회합니다. 같은 코어 시뮬레이션으로 재생한 종료 시간·별·크리스탈만 서비스 전용 RPC로 저장합니다.
- 개인 백업 업로드/게스트 가져오기로 순위표에 진입할 수 없습니다. 기존 임시 검증 기록은 백업으로 보존하되 순위표에 복사하지 않습니다. 따라서 적용 직후 순위표는 비어 있으며 새로 검증된 클리어부터 채워집니다.

## 레벨 식별

키 형식은 `<theme id>/<stable map id>@<SHA-256>`이며 커스텀 팩에는 `custom:` 접두사가 붙습니다. JSON에 `id`가 없으면 `validateMap()`이 `레벨 번호 - 1`을 문자열로 채웁니다(예: `level: 4` → `id: "3"`). 레벨 번호도 없으면 콘텐츠 기반 ID를 생성합니다. 명시된 ID는 레벨 번호가 바뀌어도 그대로 유지합니다. 따라서 슬롯을 옮길 때는 생성된 ID도 JSON에 저장해 유지하고, 다른 레벨로 교체할 때는 새 ID를 부여합니다. 같은 테마 안에 중복 ID가 있으면 서버 카탈로그가 거부합니다.

해시에는 게임플레이 데이터, 별 기준, `src/core/record-identity.ts`의 `REPLAY_RULES`가 포함됩니다. 제목, 작성자, 슬롯, 맵 테마, 편집 그룹은 제외합니다. 시뮬레이션 규칙을 바꿀 때 반드시 `REPLAY_RULES`를 올려 클라이언트와 검증기를 함께 배포합니다.

버전 없는 과거 기록은 삭제하거나 현재 버전으로 추정 변환하지 않습니다. 현재 맵의 최고 기록·별·잠금 해제에는 합산하지 않으므로 이전 진행도가 줄어 보일 수 있습니다. 새 버전을 다시 클리어하면 현재 진행으로 쌓입니다. 개인 평생 업적은 예외적으로 안정적인 ID를 기준으로 버전 간 한 번만 계산하며, 경쟁 기록으로 취급하지 않습니다. 사망 기록도 버전별로 분리됩니다.

## 배포

1. 기존 SQL을 순서대로 적용한 뒤 `20261120010000_verified_replays.sql`을 적용합니다. 크리스탈 별 및 업적 마이그레이션이 선행되어야 합니다.
2. 저장소 루트에서 `npm run build:verifier`를 실행합니다. 공식 맵과 코어를 `supabase/functions/verify-replay/verifier.js`로 번들합니다. 생성 파일은 Git에 넣지 않으며 배포 때마다 새로 빌드합니다.
3. Supabase CLI로 프로젝트를 지정하여 허용 Origin을 설정합니다(여러 개는 쉼표로 구분, 경로와 마지막 `/` 제외).

   ```sh
   supabase secrets set REPLAY_ALLOWED_ORIGINS=https://your-game.example --project-ref YOUR_PROJECT_REF
   supabase functions deploy verify-replay --project-ref YOUR_PROJECT_REF --no-verify-jwt
   ```

   `--no-verify-jwt`는 게이트웨이 검증만 끕니다. 함수는 모든 POST에서 `/auth/v1/user`로 토큰을 검증합니다. Supabase의 `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`는 함수 내부 환경에서만 사용하며 브라우저 환경 변수로 옮기지 않습니다.
4. 동일 소스의 웹 앱을 빌드·배포합니다. SQL 또는 함수 배포만으로 웹 코드는 바뀌지 않습니다. 과거 맵 버전을 받아들이려면 해당 맵을 검증기 카탈로그에 명시적으로 보관해야 하며, 현재 구현은 배포된 최신 버전만 허용합니다.

이 작업은 로컬 파일 변경이며 운영 DB·함수·웹 배포를 자동 수행하지 않습니다.

## 제한과 재시도

인증 계정별 검증 시도는 3초에 한 번입니다. 실제 요청 본문은 8 MiB, 플레이 시간은 120초, 입력 샘플은 150,000개, 클릭은 10,000개로 제한합니다. 시간은 정렬되어야 하고 샘플 간격은 최대 250 ms입니다. 재생 중 경과 시간 예산은 1.5초이며 초과하면 순위 등록을 거부합니다. 정상 클리어도 이 제한이나 호스팅 자원 제한을 넘으면 개인 기록만 남을 수 있습니다.

로그인한 공식 레벨 클리어에서만 리플레이를 보냅니다. 게스트·커스텀·편집기 테스트는 순위 등록 대상이 아닙니다. 검증 실패 시 화면에 알리고 다시 클리어할 때 재시도합니다. 리플레이를 로컬에 영구 보관하거나 자동 재전송하지 않습니다. 개인 백업의 오프라인 재시도는 기존대로 동작합니다.

재생 검증은 규칙상 가능한 클리어임을 확인합니다. 실제 사람의 입력인지, 매크로·봇이 아닌지는 증명하지 않습니다.

## 검증 명령

요청에 따라 구현 중 테스트·빌드는 실행하지 않았습니다. 직접 확인할 명령:

```sh
npm test
npm run build
npm run build:verifier
node scripts/security-db.test.mjs
```

DB 테스트는 `docs/SECURITY.md`의 PGlite 준비가 필요합니다. 추가 회귀 항목은 SHA-256 표준 벡터, 슬롯/콘텐츠 변경의 키 분리, 서버 결과 계산, 잘못된 리플레이 거부, 백업을 통한 순위 조작 차단, 서비스 전용 권한, 버전별 순위 및 사망 기록 분리입니다. 실제 함수의 인증·CORS·리소스 예산은 스테이징 배포에서도 확인합니다.
